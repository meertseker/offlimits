# Known limits

offlimits is a PreToolUse hook that reads the text of a tool call. It is not a sandbox and it does not claim to be unbypassable. This page lists every bypass and false positive we know of. If you find another, report it as described in [SECURITY.md](../SECURITY.md): it is triaged within 48 h and becomes either a fix or a line here within 7 days.

For a boundary that holds against a determined agent, give it credentials that cannot touch production in the first place. offlimits is the second line, for the common case where the agent has the access and does the obvious thing.

## Ways around the gate

- **Inline interpreters.** `node -e "require('child_process').execSync('git push origin main')"`, `python -c "import subprocess; ..."` and similar run git (or write files) from inside a program. The hook sees an interpreter call, not a push. Mitigation: add an `extraDeny` pattern for `node -e` and `python -c` in worker sessions if your agents have no reason to use them.
- **Wrapper scripts and shell aliases.** A script `./ship.sh` that runs `git push origin main`, or an alias for it, is invisible. The hook only sees the script name. Mitigation: add the script to `extraDeny`, and put it under `protectedPaths` so an agent cannot rewrite it.
- **Refspecs built from variables.** `git push origin $TARGET` with a `$TARGET` the hook does not know falls back to the current branch: it is allowed on a feature branch and denied on a protected one. So a variable that resolves to a protected branch, while the session sits on a feature branch, is not caught. A variable set earlier in the same command (`T=main; git push origin $T`) is resolved. Only `$(...)`, backticks and other complex forms (`${T/x/y}`, `"$A$B"`) are unsure: ask in solo mode, deny for a worker.
- **Git aliases from your git config.** An alias defined in `~/.gitconfig` or `.git/config` (`git ship` for `push origin main`) is not resolved; the hook sees `git ship`. Aliases passed with `git -c alias.x=...` on the command line are resolved, and `git config alias.*` writes are denied.
- **Remote URL instead of remote name.** `git push git@github.com:acme/app.git main` is judged by its refspec (`main`), which works, but `git push <url>` with no refspec cannot tell which remote it is and falls back to the current branch.
- **Wrapper chains deeper than 8 levels** (`bash -c "bash -c \"...\""` and so on) stop being expanded. The innermost command is not inspected; the call counts as opaque (`opaque-shell`: ask in solo mode, deny for a worker).
- **Redirect targets that are not literal.** `echo x > $(pwd)/offlimits.json` or `> $FILE` cannot be resolved, so a write to a protected file through them is not caught.
- **`xargs`.** `... | xargs rm` writes or deletes files without naming them in the command, so it is not caught. `find -exec` and `-execdir` are handled differently: a write command after them (`find . -name offlimits.json -exec rm {} \;`) counts as unsure, so it asks in solo mode and is denied for a worker, whatever `find` would match.
- **SQL inside `psql -c`.** A `psql -c "DROP TABLE ..."` against a remote host is blocked because the host is remote (`remote-db`), but the SQL itself is never inspected. Only SQL sent through the Supabase MCP `execute_sql` tool is read. Against a local database, `psql -c` is always allowed.
- **MCP servers with unusual tool names.** The built-in MCP rules know the Supabase, Vercel and GitHub servers. On any other server, `mcp-destructive` only catches tool names that start with a destructive verb (`delete`, `deploy`, `drop`, `push`, `merge` and so on), and SQL tools that run write SQL. A write tool with a mild name (`update_record`, `apply_changes`) is covered only if you list the server in `production.mcpServers`. Reads are recognised by a name prefix (`get_`, `list_`, `search_`, and so on); anything else on a listed server is denied.
- **Raw HTTP calls to an API.** `curl -X PUT https://api.github.com/repos/acme/app/contents/x`, or a `fetch` from a script, changes a repository or a production service without any CLI the hook knows. HTTP clients are out of scope: give the agent a token that cannot write to protected branches.
- **`npm run <script>` and other task runners.** `npm run ship`, `make deploy` or `just release` run whatever the script says. The hook sees the script name, not its body. Mitigation: add the script name to `extraDeny`, and protect the file that defines it (`package.json`, `Makefile`) with `protectedPaths` if it matters.
- **Paths the hook cannot spell out.** Write targets built from variables (`rm $F`) or from `xargs`, Windows 8.3 short names (`OFFLIM~1.JSO`), NTFS alternate data streams other than `::$DATA`, symlinks that point into a protected directory, and archive extraction (`tar -x`, `unzip`) are not resolved.
- **Directory changes the hook cannot follow.** After `cd -`, `popd` or `cd $DIR`, the working directory is unknown. A relative write target that names a protected segment (`settings.json`, `.claude`, `..`) or a glob then asks (solo) or is denied (worker); any other relative target, for example `ci.yml` after `cd $DIR` into `.github/workflows`, is not caught.
- **The hook has to run.** Hooks do not run inside a `claude -p` subprocess that was started without the plugin, in a session where the plugin is disabled, or in another tool that does not read Claude Code's hook configuration. An agent that can start such a process can act outside the gate.
- **The human can change the policy.** The policy file and hook config are write-protected from the agent, but not from you. Editing `offlimits.json` or `.claude/settings.json` mid-session changes what the gate enforces, by design.
- **The role comes from the environment.** Anyone who can start the session decides its role. The `role-spoof` rule stops an agent from assigning the variable in a command, but cannot stop a parent process that is not the agent.

## False positives

- **`git push --dry-run` to a protected branch is denied.** The hook does not special-case dry runs. It is conservative on purpose; run it yourself, or add an anchored `allow` pattern.
- **Unusual read tools on a listed server.** On a server in `production.mcpServers`, any tool that does not start with a read verb is denied, including harmless ones with unusual names.
- **SQL is judged lexically, not parsed.** An `execute_sql` call passes only when every statement starts with `select`, `with`, `explain`, `show`, `values` or `table` and no write keyword or write function (`setval`, `pg_terminate_backend`, `set_config` and others) appears outside comments, string literals and quoted identifiers. `select ... for update`, `nextval(...)` or a column named `copy` without quotes count as writes.
- **`disableAllHooks` anywhere.** Any `Write`, `Edit`, `MultiEdit` or `NotebookEdit` input that contains the text `disableAllHooks` is denied, whatever the file, and so is a shell command that mentions it and writes anything. Read-only commands such as `grep disableAllHooks` pass.
- **Glob targets are judged broadly.** `rm *.json` or `rm -rf *` is denied when the glob could match a protected path, even if the shell would not expand it that way (bash `*` skips dotfiles; the hook does not).
- **Copies into a directory.** `cp x .github` (a directory that is not the repository root) is judged as if `.github` might be replaced, so a recursive copy onto a parent of a protected path is denied.
- **`allow` patterns are unanchored regexes.** `"allow": ["vercel"]` matches every segment that contains `vercel`, so `vercel --prod` passes too. Anchor them: `"^vercel env pull( |$)"`, `"^git push origin feat/[\\w./-]+$"`.
- **Opaque shells.** `bash`, `sh` or `pwsh` reading commands from stdin cannot be inspected, so the call asks (solo) or is denied (worker). This is rule `opaque-shell`.
- **Very large commands.** So that the hook always answers well inside Claude Code's hook timeout, a shell command longer than 64 KB, with more than 1000 distinct segments (nested ones included), more than 200 tracked variables, more than 8192 PowerShell script blocks or hash tables, more than 1 MB of nested command text in total (bodies of nested shells, substitutions and script blocks, each counted every time it is read), or subexpressions (`"$(`) nested more than 100 deep is not inspected: it counts as `opaque-shell` (ask in solo mode, deny for a worker). Within one command, a brace expansion of more than 256 words, more than 4096 brace words in total, or more than 256 distinct write targets in one segment makes the write target unsure (`protected-file`), more than 32 bare `--` in one segment is `opaque-shell`, and after 16 distinct directories (or 3 s spent) the hook stops asking git for the current branch, so a later push with no refspec is unsure.
- **Switching away from a protected branch and pushing in one command.** On `main`, `git checkout feat/x && git push` is still denied: the hook checks the branch the session is on as well as the one the command switches to. Run the two steps as separate commands.
- **Heredoc bodies are scanned.** The hook does not know where a heredoc ends, so its lines are checked as commands. `cat > notes.md <<EOF` followed by a line `git push origin main` is denied even though nothing is pushed. Write such files with the file tools instead.

## Team mode

- **`team board worker`-style false positive.** For a worker, the `team-launch` rule looks for `worker`, `done`, `coordinator`, `init` or `start` among all arguments after `team`, not only the first one. A worker running `team board worker`, or `team stage building done` with an extra word, is denied although those commands are harmless. Rephrase the question or hand over to the coordinator.
- **The launcher relies on `CLAUDECODE` and the gate rule.** The CLI refuses privileged commands inside Claude Code unless the role is coordinator; a subagent of the coordinator inherits that role, so the second layer is the `team-launch` rule, which resolves subagents to worker. A worker could run a different launcher of its own (a script that calls `git worktree` and `claude`); starting the agent is still blocked by `agent-spawn`, but anything that is not an agent CLI is outside the rule.
- **Terminal launchers.** `start`, `Start-Process`, `wt`, `x-terminal-emulator`, `xterm`, `konsole`, `gnome-terminal` and `osascript` `do script` are unwrapped and the command they open is checked like a nested shell. Forms that stay out of reach: launchers not on that list (`tmux new-window`, `screen`, `open -a Terminal`, `kitty @ launch`), a command written to a script file and then opened, and arguments assembled at run time (`osascript` scripts without `do script`, `Start-Process -ArgumentList $args`; these are treated as opaque and denied for workers). `wt` is read the way Windows Terminal reads it: every unescaped `;`, also one inside an argument, starts a new tab, also when `wt` is not the first command of a `cmd /c` body. PowerShell lead-ins (`$p = cmd`, `$x += cmd`, `[type]$p = cmd`, `[void](cmd)`, `. cmd`) are dropped before the check, for the PowerShell tool and for `pwsh -c` bodies; a PowerShell command run from the Bash tool without `pwsh -c` is read with Bash rules. PowerShell script blocks `{ ... }` (also nested, and those passed to cmdlets such as `ForEach-Object`, `Where-Object`, `Invoke-Command`, `try`/`catch`, `switch` and `function` bodies) and hash-table values `@{ k = cmd }` are read as commands, for the PowerShell tool and for `pwsh -c`, `iex` and `Invoke-Command` bodies; a hash-table value that is a quoted literal, a number, `$true`, `$false` or `$null` is not a command. A hash-table key that is not a plain word or quoted literal (`(1) = ...`, `"$(...)" = ...`) is read as a command too, and an entry with several words but no top-level `=` counts as `opaque-shell`. In PowerShell text, `<# ... #>` is read as a comment, a backtick escapes the next character, `@"..."@` and `@'...'@` here-strings are read whole, and the curly quotes (`‘ ’ ‚ ‛` and `“ ” „`) are read as quotes, as PowerShell reads them; Bash text is read as before. One known false positive stays: a `#` right after a closing quote or parenthesis (`$a = "x"#{`) is not taken as a comment, so a brace in it counts as unbalanced. Braces that do not balance (outside quotes, `${name}` and comments) count as `opaque-shell` (ask in solo mode, deny for a worker). Not resolved: `& $c` or `. $c` with a variable command name (`$c = "git"; & $c push origin main`), variables set inside a script block (`1 | % { $b = 'main' }; git push origin $b` does not know `$b`), a script block stored in a variable and run later (`$s = [scriptblock]::Create('...'); & $s`), and cmd's own quoting rules beyond `"` and `^` (a `cmd /c` body is read with shell-style quotes, so a cmd command line that relies on unusual quoting may be split differently than cmd splits it). In a `cmd /c` body, cmd lead-ins before a command (`@`, `call`, `if [/i] [not] <condition>`, `else`, `for ... do`, `start`, a nested `cmd /c`) are dropped and the command after them is checked, also when it is `wt`.
- **A text-reading gate cannot enumerate every launcher.** New terminal programs, scripts written and then run, and arguments assembled at run time will always exist. For a boundary that holds against a determined agent, give workers credentials that cannot push to protected branches (and no deploy tokens); the gate then catches honest mistakes and the credentials stop the rest.
- **Hidden team subcommands.** A worker's `team $T` or `team $(echo start)` is denied because the subcommand is not visible, but `xargs team`, `echo start | xargs team` and `cp team.mjs x.mjs && node x.mjs start` are not recognised: the rule sees no `team`. The CLI guard still refuses explicit workers (`OFFLIMITS_ROLE=worker`); a subagent of your own `defaultRole` session does not have that role variable.
- **Importing the CLI through an inline interpreter.** A coordinator's subagent that deliberately runs `node -e "import('.../hooks/lib/team/cli.mjs')..."` inherits the coordinator role, so the CLI's own check passes, and the `team-launch` rule sees an interpreter call, not `team`. Both layers pass. This is the same class as the inline-interpreter limit above; an `extraDeny` pattern for `node -e` closes it.
- **The lock is advisory and file-based.** `.offlimits/team/lock` protects the launcher's own writes. A process that edits `board.json` or `reservations.json` directly ignores it, and on a network or synced folder file locks can behave differently.
- **Terminals.** `terminal: auto` uses Windows Terminal (`wt`) on Windows and falls back to `cmd /c start` with PowerShell when `wt` is missing; Terminal.app on macOS; on Linux `x-terminal-emulator`, `gnome-terminal` or `konsole`, in that order. Only when nothing fits (or the paths cannot be carried safely by the chosen terminal) does the launcher print the exact command for a human to run, which matters in night mode.
- **Repository and brief paths are allowlisted.** The worker's terminal command can only carry letters, digits, space and these characters: `.` `,` `:` `\` `/` `_` `(` `)` `-`. Any other character in the repository or brief path is refused, including `~ + & ' @ # [ ] = %` and `"`, and `team worker` stops with an error until the repository lives at a path without them.
- **Squash merges.** `team done` checks git ancestry, so a squash-merged lane looks unmerged and needs `--abandon`.

## Platform notes

- The hook needs Node 20 or newer on the PATH of the machine running Claude Code.
- If the hook itself crashes, `onError: "auto"` blocks only for workers. Coordinator and solo sessions allow the call and log the error; the warning appears in the next session banner (and in `/offlimits`), not at the moment of the call. A solo user who wants fail-closed sets `"onError": "block"`.
